# Linux x86-64 temporary object creation comparison

Measured on November 19, 2026, in Europe/Istanbul. Compare the optimized gutil
0.17.0 development executable at `5c9f01081c19baf6f683e1bfa6f9be810c7903e6` with
GNU Coreutils `mktemp` 9.12. The gutil executable uses OS randomness, atomic
reservation, explicit file close, an ordered asynchronous worker, and its
native template parser. No older gutil baseline implements this command.

## Compared workloads

Each invocation handles one name, matching the single-object interface of GNU
mktemp. Both programs run on logical CPU 3 with `LC_ALL=C`, `TZ=UTC`, umask
022, and `TMPDIR` set to the same prepared fixture directory. gutil receives
`--no-config --progress=never --jobs=1 mktemp`; GNU receives the arguments
after the utility name directly.

| Workload | Arguments after the utility name | Verified result |
| --- | --- | --- |
| `file` | `object.XXXXXXXXXX` | One empty regular file, mode 600, relative output |
| `directory` | `-d object.XXXXXXXXXX` | One empty directory, mode 700, relative output |
| `default-tmpdir` | No arguments | One empty file in `TMPDIR`, mode 600, absolute output |
| `dry-run` | `-u object.XXXXXXXXXX` | An unused relative name; no filesystem objects created |
| `quiet-missing-parent` | `-q missing/object.XXXXXXXXXX` | Status 1, no output or diagnostics, no filesystem objects created |

The fixture is reset before each invocation. Setup, cleanup, and verification
of name shape, location, type, size, permissions, object count, and failure
state are outside timed intervals. Each timed interval includes process
startup, command execution, stdout/stderr capture, and waiting for exit.
No durability synchronization beyond the utility's normal behavior is added.

Four warmup rounds precede 30 measured rounds per workload. Seed 42 shuffles
the two executables within each round. Saved release executables are immutable
and identified by SHA-256 in the raw samples. No local compilation or test
suite runs during measurement; ordinary desktop background activity remains
possible.

```sh
# Build source 5c9f010 with cargo build --locked --release -p gutil,
# then save its executable at the immutable path below.
taskset -c 3 python3 benchmarks/mktemp.py /tmp/gutil-mktemp-checkpoint \
  --gnu /usr/bin/mktemp --rounds 30 --warmup 4
```

## Elapsed-time results

Values are medians with inclusive interquartile ranges. Paired reductions use
`100 * (GNU - gutil) / GNU` within each round. Negative values indicate higher
gutil elapsed time. IQRs describe sample spread rather than confidence bounds.

| Workload | gutil ms [IQR] | GNU ms [IQR] | Paired reduction % [IQR] |
| --- | ---: | ---: | ---: |
| file | 2.557 [2.491–2.753] | 1.225 [1.189–1.412] | -105.720 [-112.808–-98.009] |
| directory | 2.505 [2.473–2.548] | 1.215 [1.179–1.242] | -105.093 [-115.398–-100.710] |
| default-tmpdir | 2.506 [2.466–2.541] | 1.249 [1.202–1.290] | -100.120 [-109.895–-94.513] |
| dry-run | 2.473 [2.432–2.513] | 1.189 [1.133–1.237] | -105.940 [-117.323–-100.522] |
| quiet-missing-parent | 2.444 [2.418–2.484] | 1.173 [1.144–1.241] | -110.641 [-114.424–-99.406] |

GNU has lower elapsed time in every measured workload. gutil medians range
from 2.44 to 2.56 ms, while GNU medians range from 1.17 to 1.25 ms. Every paired
reduction and its IQR is negative. These observations leave a clear latency
gap for further performance work.

The similar medians across creation, dry-run, and failure cases are consistent
with fixed invocation costs. This is an inference; the measurements do not
isolate loader, parser, runtime, worker-startup, or random-source costs.
No improvement over GNU or older gutil is established by these samples.

## Scope and raw samples

These measurements cover warm single-object invocations on Linux tmpfs, with
executables stored on ext4. They do not establish physical-storage throughput,
Windows or macOS performance, collision-heavy behavior, default-ACL behavior,
or a batch throughput advantage. Native mode and path behavior, collision
preservation, entropy/close failures, and template semantics have separate
regression coverage. The full Coreutils implementation and project-wide
performance target remain unfinished.
