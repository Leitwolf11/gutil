# Linux x86-64 stream duplication comparison

Measured on November 19, 2026, in Europe/Istanbul. This comparison measures
new `gutil tee` against GNU Coreutils `tee` 9.12. The candidate is
`4a0a14f` on `feature/tee`, declaring gutil 0.15.0. Both commands copy the
same input bytes to standard output and the same number of output files.

| Build profile | Default optimized Cargo release profile; no custom LTO or linker flags |

## Workload and method

Each process copies a 32 MiB file containing bytes 0 through 255 repeated
131,072 times. Stdin is either a regular file or a pipe fed by Python in
128 KiB chunks. Stdout goes to `/dev/null`; zero, one, or four additional
files are created on tmpfs. Processes use `LC_ALL=C` and `TZ=UTC`.
gutil receives `--no-config --progress=never --jobs=1 tee`; GNU runs `tee`.
The one-worker runtime preserves stream order. The CPU affinity gives both
implementations the same single-logical-CPU budget.

Before timing each workload, the harness hashes stdout and every output file
against the input SHA-256 digest. It verifies every timed file after the timed
interval. Fixture generation, deletion of previous output files, and checksum
verification are excluded. Process creation, opening files, input copying,
stdout writes, and waiting for completion are included. Pipe measurements
also include the Python feeder; they are end-to-end pipeline measurements.

Four warmup rounds precede 30 recorded rounds for each workload. Seed 42
shuffles the order of the two commands in every round. The table reports
median elapsed milliseconds with inclusive interquartile ranges. Paired
reduction is `100 * (GNU - gutil) / GNU` for each round; positive values mean
less elapsed time for gutil. IQRs describe sample spread, not confidence
intervals.

```sh
cargo build --locked --release -p gutil
cp target/release/gutil /tmp/gutil-tee-4a0a14f
taskset -c 3 python3 benchmarks/tee.py /tmp/gutil-tee-4a0a14f \
  --gnu /usr/bin/tee --mib 32 --rounds 30 --warmup 4
```

The recorded run used the checked-in harness.
The candidate executable remained immutable throughout measurement. No local
build or test suite ran during the recorded comparison. This is a shared
desktop with ordinary background activity; interleaving reduces temporal bias
but does not remove scheduling, thermal, or memory-pressure variation.

## Results

| Stdin / additional files | gutil ms [IQR] | GNU ms [IQR] | Paired reduction % [IQR] |
| --- | ---: | ---: | ---: |
| file-stdin/0-files | 8.05 [7.98–8.13] | 8.89 [8.85–8.97] | 9.71 [9.26–10.51] |
| file-stdin/1-files | 17.71 [17.39–17.74] | 21.01 [20.92–21.09] | 15.71 [15.28–17.02] |
| file-stdin/4-files | 45.76 [45.55–45.94] | 55.08 [54.64–55.70] | 17.15 [16.32–17.83] |
| pipe-stdin/0-files | 19.94 [19.88–20.08] | 21.25 [21.10–21.35] | 6.21 [5.03–6.73] |
| pipe-stdin/1-files | 30.87 [30.77–30.96] | 37.56 [37.42–37.77] | 17.92 [17.17–18.39] |
| pipe-stdin/4-files | 59.32 [58.99–59.58] | 76.14 [75.99–76.61] | 22.05 [21.76–22.84] |

On this host, regular-file stdin shows median paired reductions of 9.7–17.2%,
and pipe stdin shows 6.2–22.1%. The pipe-to-null case has the smallest margin;
the one- and four-file pipe cases have reductions of 17.9% and 22.1%.
These are measured elapsed-time differences for the listed workloads, not a
universal performance guarantee. Output-file and owned stdout-handle close
errors are checked in this candidate; neither implementation requests an
additional `fsync` durability guarantee.

## Scope

These workloads use warm, memory-backed files, with no `fsync` durability
requirement. They do not establish physical-storage performance or behavior
on Windows or macOS. Startup-dominated tiny inputs, terminals, FIFOs, append
mode, and failing destinations require separate measurements. Byte forwarding,
append and overwrite semantics, error policies, broken pipes, partial-line
forwarding, Unix interrupts, and native paths have integration coverage.

Binary SHA-256 identities and raw samples are recorded in the accompanying
[JSON result](2026-11-19-linux-x86-64-tee.json).
